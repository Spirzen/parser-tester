Кодировки и «кракозябры»

Битый текст — не магия и не «сломанный сайт». Это одна лишняя или одна пропущенная попытка интерпретировать байты. Разбираем три места, где ошибка возникает, и лечим каждое.

Три уровня, на которых можно ошибиться

  1. Заголовок сервера. Content-Type: text/html; charset=windows-1251 — самый надёжный источник: requests подставляет его в r.encoding.
  2. Мета внутри документа. <meta charset="utf-8"> или старый <meta http-equiv="Content-Type" content="text/html; charset=cp1251">. Сервер мог соврать, а файл — нет.
  3. Разбор и вывод. Парсер получил строку, а вы печатаете её в консоль Windows с кодировкой cp866 — текст «портится» уже на экране, данные целы.

response.text и response.content

У requests есть два способа забрать тело, и путаница между ними стоит больше всего битых отчётов.

Что берёмТипКак появляетсяКогда нужно
r.contentбайтыровно то, что прислал сервервсегда как исходная точка: свой decode, запись в файл, картинки, gzip
r.textстрокаcontent.decode(r.encoding)когда доверяете заголовку charset
r.encodingстрока или Noneиз Content-Type, иначе None → apparent_encoding по содержимомупроверить и при необходимости перезаписать
r.apparent_encodingстрокадогадка по частотам байтовподсказка, не истина: часто путает UTF-8 и windows-1251
 
import requests
from bs4 import BeautifulSoup

r = requests.get("http://localhost:8000/http/charset", timeout=10)
print(r.headers["Content-Type"])   # text/html; charset=windows-1251
print(r.encoding)                  # windows-1251 — заголовок важнее мета-тега

# Плохо: encoding может быть угадан неверно, тогда кракозябры.
soup_bad = BeautifulSoup(r.text, "html.parser")

# Хорошо: сами декодируем байты той кодировкой, которую объявил сервер.
html = r.content.decode("cp1251", errors="replace")
soup = BeautifulSoup(html, "html.parser")
print(soup.select_one("h1").get_text(strip=True))   # Щука и флинт

Порядок поиска кодировки. Заголовок Content-Type → meta charset в файле → apparent_encoding как последняя догадка → ручная проверка на редких символах (Ñ, Ã, ï»¿, ).

Шпаргалка кодировок

utf-8
Современный стандарт сайта, до 4 байта на символ; кириллица — 2 байта.
windows-1251
cp1251: кириллица в одном байте, встречалась на старых русскоязычных сайтах.
koi8-r
Советская 8-битная раскладка, до сих пор встречается в почтовых заголовках и логах.
cp866
Кодировка консоли DOS: из-за неё битый вывод в терминале Windows.
iso-8859-1
latin-1: по стандарту HTTP «значение по умолчанию» для text/* — источник главных недоразумений.

Локальная мишень: страница в windows-1251

На полигоне есть специальная «старая» страница — эндпоинт /http/charset. Он живёт только на локальном сервере: его отдаёт node tools/serve.mjs, на GitHub Pages таких эндпоинтов нет. Запуск: node tools/build.mjs, затем node tools/serve.mjs, затем адрес http://localhost:8000/http/charset.

Ответ приходит с заголовком Content-Type: text/html; charset=windows-1251 и телом в однобайтовой кириллице. Три упражнения:

  • Прочитать через r.text и убедиться, что requests угадал заголовок правильно.
  • Принудительно декодировать байты как utf-8 и прочитать исходную фразу без потерь.
  • Сохранить r.content в файл, открыть редактором с ручной сменой кодировки и увидеть разницу между cp1251 и latin-1.

Тот же приём работает с реальными «старыми» сайтами, но помните про правила парсинга: заголовок User-Agent, пауза и robots.txt обязательны и для одностраничной мишени.
